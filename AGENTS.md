# uniconnect

Sponsorship matching prototype that connects student groups (학생단체) with brands (브랜드). It is a pnpm workspace with a React frontend and an Express API. The UI copy is Korean.

## Commands

Run these from the repo root:

- `corepack pnpm@10.34.3 install` installs every workspace package.
- `npm run dev` starts the API on http://localhost:4000 and Vite on http://localhost:8443. Vite proxies `/api` to the API. The API reads `backend/dev.env` and, when it exists, `backend/.env.local`, the git-ignored home of private keys such as `KAKAO_REST_API_KEY`; never write a key into a tracked file.
- `npm run typecheck` runs tsc for the backend and the frontend.
- `npm test` runs the backend tests (`node:test` through tsx: the API in `app.test.ts`, and the Postgres store in `store.postgres.test.ts` on PGlite, an in-process Postgres, in its own process), then the frontend unit tests (vitest, `frontend/src/**/*.test.ts`, configured in `frontend/vitest.config.ts` without the app's Vite plugins). `frontend/src/lib/appPaths.sync.test.ts` checks `backend/src/lib/appPaths.ts` against `route.ts`.
- `npm run e2e` (after `npm run build`) runs the Playwright browser tests in `e2e/` against the built app on port 4300 with a fresh temp data file, in the installed Chrome (`channel: "chrome"`, no browser download): the main flows and axe accessibility checks (WCAG 2.1 A/AA; critical and serious problems fail).
- GitHub Actions (`.github/workflows/ci.yml`) runs install, typecheck, test, build and e2e on every push to main and every pull request.
- `npm run build`, then `npm start`, builds both packages and serves the API plus the built frontend from Express.

## Project Structure

- `frontend/src/App.tsx` holds the app state and the API calls, and switches between pages and modals for the current role.
- `frontend/src/api/` has the fetch wrapper with the Bearer token (`client.ts`) and one function per endpoint (`index.ts`).
- `frontend/src/pages/`, `modals/`, `layout/` and `components/` contain the UI. `data/`, `lib/` and `hooks/` contain constants and helpers.
- `frontend/src/layout/Header.tsx` is the fixed header: the logo on its own, then floating pills for the role's menu on wide screens, the next event, account buttons and Menu (on the introduction a visitor gets its sections and 회원가입 instead of the menu; on a member screen shown to a visitor, a `예시 화면` chip sits by the logo) (registering is on the 내 행사 and 행사 일정 calendars and in Menu). The logo switches to its light version (`assets/brand/uniconnect_horizontal_reversed.svg`) over deep blue surfaces. `NavMenu.tsx` is the full-screen silver menu behind Menu and `Footer.tsx` the footer: the site's links, headed on the introduction (sign up, get the app) and the dashboard by a deep blue mesh card with linked chrome rings and the call to register (the whole footer is left out of a conversation).
- `frontend/src/scenes/` holds the WebGL effects: getlayers.ai's Antipode gradient (the introduction's and dashboards' hero, detail banners) and Interference gradient (reports, measurement, analytics), run by `LayersGradient.tsx` from `shaders.ts`; Stride's mesh gradient, drawn once into an image (`MeshBackdrop.tsx`); and its chrome chain and rings (`ChromeScene.tsx`, `chromeModels.ts`).
- `frontend/src/index.css` is the single global stylesheet. Components use its class names, so a renamed class must change in both places.
- `backend/src/routes/` has one Express router per resource.
- `backend/src/data/seed.ts` holds the demo accounts and data.
- `backend/src/store.ts` holds the data in memory as one document and writes it through `lib/storage.ts`: to `backend/data/db.json` (gitignored; delete it to reseed), or, when `DATABASE_URL` is set, to Postgres (`lib/sql.ts`: Neon's HTTP driver, or a `useSql` test database), which every copy of the API shares. `ensureTables` makes the tables on first use and runs a `create table` once more when a copy starting at the same moment made it first (Postgres answers 23505 or 42P07 then). Each write carries the version it builds on (`StaleWrite` when another copy wrote first), and with shared storage each `/api` request first calls `refreshDatabase()`, which reads the data again when the stored version moved on (at most every `freshness.everyMs`). Agreement photos go through `lib/photos.ts` (files under `uploads/`, or rows in Postgres).
- Vercel runs the built frontend as static files and the API as one function, `api/index.mjs` → `backend/src/vercel.ts` (it loads the data on each copy's first request through `createApp`'s `loaded`); `vercel.json` holds the build, the routes (the app's addresses, as in `appPaths.ts`, get `index.html`; anything else gets `404.html`, a copy of it the frontend build makes, with a 404 status; the rewrites match strictly, so `trailingSlash: false` first redirects an address ending in a slash to the one without it), the region (`sin1`, beside the Neon database) and the security headers, which must match `app.ts` (a test compares them). Background work after a response needs `waitUntil` from `@vercel/functions`, as `notify` does; nothing may rely on timers or files lasting there.

## Conventions

- The UI is in Korean or English (`frontend/src/i18n`): the choice made in 내 정보's 언어 row or with the footer's switch, else Korean when the browser's first language is Korean and English for any other (Korean in unit tests, which have no window). Copy is written in Korean and wrapped in `t("…", values)`; the Korean is the key and its English lives in `i18n/en/<area>.ts` (`{name}` parts filled from `values`). Never translate values used in logic (roles, NavLabels, statuses, sponsor kinds, tab values): show them with `t(value)`, and keep their English in `i18n/en/common.ts`. `i18n/coverage.test.ts` fails for a `t()` sentence without English, `i18n/lists.test.ts` for a listed value. Dates and money follow the language (`lib/date.ts`, `formatWon`, `fullWon`, `manWon`/`wonUnit`). The client sends the language as `Accept-Language`; the server still writes its messages in Korean and answers them in English through `backend/src/lib/i18n.ts` and `backend/src/i18n/en.ts` (`{name}` patterns for messages with a value). The legal pages show an English translation with a note that the Korean original prevails. Emails stay Korean.

- `frontend/src/types.ts` mirrors the API shapes in `backend/src/types.ts`.
- Account types and sponsor types are listed in both `backend/src/lib/validation.ts` and the frontend (`data/roles.ts`, `data/sponsorTypes.ts`). Change them together. The frontend shows account types in groups (`accountTypeGroups`, flattening to the same order), and `catalog.ts` files each under one of the eight industries the match and the marks use; a renamed type goes in `renamedAccountTypes`, which the store applies on load. Sign-up asks for the person running the account (`contact`: name, position, a mobile number stored as 010-1234-5678 by `parseContact`), changed from 내 정보 (`PUT /api/auth/contact`, `modals/ContactModal.tsx`) and shown to no one but the two sides of an accepted proposal, on its agreement; the privacy policy says so. The same goes for profile fact labels and SNS platforms (`validation.ts` and `data/profile.ts`) and question kinds (`data/inquiries.ts`); `frontend/src/lib/lists.sync.test.ts` fails when they differ.
- Proposals go both ways through `POST /api/proposals`: a student group's reaches a brand with an account as a `SponsorRequest` (`/api/requests`, the brand's 받은 제안), a brand's reaches a group with an account as a `SponsorOffer` (`/api/offers`, the group's 받은 협찬, `pages/OffersPage.tsx`). Both inboxes share `components/RequestProgress.tsx` and the `request-*` classes, and `/api/proposals` answers each side's statuses. A proposal to a partner with an account is about the sender's next event or campaign that has not ended, and needs one (409 otherwise), so an accepted one always becomes a dated sponsorship; one waiting for an answer is not sent twice, an accepted one can be sent again only about a later event, and withdrawing then takes back only the waiting one.
- A listing's `logo` is a PNG, JPEG or WebP data URL of about 100KB at most, resized in the browser (`lib/image.ts`) and checked in `routes/profile.ts` (left out keeps it, null removes it); it lives in db.json for now.
- The brand and group catalogs are editable listings: each account's own listing is linked by `brandId`/`groupId` and edited from 내 정보. Recommended matches are the other catalog's top three, worked out in `backend/src/lib/catalog.ts`.
- Members (accounts that signed up) see only members' listings. The seed catalog and the demo accounts' listings are the examples, seen by visitors and by the shared demo accounts, which stay as trial logins; the login popup logs into either with one press (`data/demo.ts`, kept equal to the seed by `lib/lists.sync.test.ts`). The two never meet: `shownTo`/`shownCatalog` in `lib/catalog.ts` decide the catalogs and matches, proposals and conversations accept only a partner the account sees (404 otherwise), a member's proposal list and conversations leave out the examples, 가까운 순 shows a shop as its brand only to those who see that brand, and the demo group can't invite shops (403), as an invitation reaches a real owner. A member's empty catalog says so with what to do meanwhile (`components/CatalogEmpty.tsx`, once App's `catalogReady` says it has loaded), and 추천's heading stops claiming it found any. App empties every list in the same render the viewer changes (`listsFor`; an effect would draw the last viewer's data for a frame), so the examples never flash after logging in. The bell lists only what exists (no recommendation notice without matches) and shows its dot only when it has notices. Each listing's `score` (55–98), `reasons` and `scoreParts` (each part as a share of its best, 0 to 1, with a short label the detail page shows as a bar; the labels' English is listed in `i18n/lists.test.ts`) are worked out for the account browsing, or the demo account of that side for visitors, in `backend/src/lib/matchScore.ts`: industry fit 35, shared tag words 15, track record 20 (a brand's sponsorships, a group's event size), sponsored together before 15, ready to answer 15. The `score` stored on a listing is not used.
- Distances on the catalogs (단체 찾기's 가까운 순 tab, the pin chip on `WorkCard`) are straight-line km between a group's campus and a brand's store, worked out in `browse()` with `lib/geo.ts`. A campus comes from the table in `backend/src/data/campuses.ts` (each university's own feature in OpenStreetMap, with its road address beside it; add schools the same way), found by the account's email domain, else the school name. A brand's store is `location` on its listing, written as `address` from 내 정보 and placed on the map through OpenStreetMap's Nominatim (`lib/geocode.ts`) only when `NOMINATIM_URL` is set (`backend/dev.env` sets the public server; it takes one request a second, so lookups are spaced 1.1s apart, and its ODbL data may be kept with the `Map data © OpenStreetMap contributors` credit in the footer). Never store coordinates from Kakao's or VWorld's geocoders: both allow live use only. Catalog version 4 dropped the Kakao coordinates saved before. Without coordinates there is no distance, and the save notice and the edit form say so. Tests and the e2e server run without a geocoder or a Kakao key. Distance never changes the match score. The privacy policy names the OpenStreetMap Foundation for this.
- The 가까운 순 tab on 추천 매칭 (`components/NearbyPlaces.tsx`) lists real shops around the student group's campus (the demo group's for visitors) from Kakao Local's category search, as the other tabs' cards (WorkCard's classes) with 협약 전 where a partner's card offers a proposal: every kind merged at first (`category=all`, the nearest 30), or one kind. A chain's branch shows its logo (`lib/franchises.ts` matches the name's start, `data/franchises.ts` holds the PNGs from Wikimedia Commons in `assets/franchises/`: public domain as artwork, still trademarks, so add a chain only with its logo's licence checked), any other shop its name's first letter; `GET /api/places` in `routes/places.ts` with `lib/places.ts`, the kinds listed in `validation.ts` and `data/places.ts`. Kakao allows Local API results only as live answers shown on screen: never store or cache them (only a place's ID and Kakao Map URL may be kept), so each look asks Kakao again and the route is rate-limited per address instead, counting each kind asked. Tests swap `placeSearch.search`. Each shop comes with its point, used only to draw `components/PlaceMap.tsx` (the 목록 · 지도 switch: a sketch around the campus, scaled to the farthest shop by `lib/placeMap.ts`, with stacked dots spread apart), never kept. A 협약 전 shop can be invited (`routes/invites.ts`, `modals/InviteShopModal.tsx`): a `ShopInvite` in `Database.invites` keeps only the place's ID and Kakao Map URL, and its page `/invite/<code>` (`pages/InvitePage.tsx`, the brand side for visitors) lets the owner sign up as a brand and link the shop with one press, which lists the brand at once with `kakaoPlaceId` on its listing (one shop per brand, one brand per shop) and emails the groups that invited it; 가까운 순 then shows that shop as the brand, with a proposal.
- The catalogs can be searched (`components/CatalogSearch.tsx`, `matchesQuery` in `lib/search.ts`: every word typed, in name, kind, offer, tags, school or event), and 단체 찾기 also filters by the next event's size and month and by school (`matchesGroupFilters`). Search and filters apply to whichever tab is open and stay when the tab changes.
- Student groups and brands have separate menus and pages (`data/navigation.ts`). A feature for one side gets its own page rather than a role branch inside the other side's page.
- Every screen is a `View` with its own address (`lib/route.ts`), title and description (`lib/pageMeta.ts`). `/` is the introduction for visitors (`home`, `pages/LandingPage.tsx`) and the dashboard lives at `/dashboard`; a member opening `/` goes on to the dashboard, and nothing shows there while a saved session is checked. History entries keep their view, and `entryView` drops one that no longer fits its address (kept from before the dashboard moved). An address no screen has becomes a `missing` view, the 404 page; `backend/src/lib/appPaths.ts` lists the same addresses so the server answers the rest with a real 404, and `vercel.json`'s rewrites list them again for Vercel, so change the three together (`appPaths.sync.test.ts` checks). Screens for one account or one link, and the dashboard, carry `noindex` in their meta (`keepOutOfSearch`, also called by the check-in pages); the rest are open to search engines (`robots.index` in `frontend/.figma/make/site.json`, `public/robots.txt`), and `public/llms.txt` describes the site for AI agents. Change screens through App's `go` and `goBack`, never by setting state directly, so the browser's back and forward buttons and swipe gestures keep working. `lib/swipe.ts` adds swiping anywhere on the page through those entries (one finger, or two on a trackpad: left to right goes back, right to left forward), leaving swipes from the screen edge to the browser; `go` tells it through `noteHistoryEnd` how far forward history reaches, and the screen a swipe brings slides in from that side (`data-swiped` in the "Motion" section).
- Popups go inside `<Presence>` (`components/Presence.tsx`) so they animate closed however they are closed.
- The scenes load three.js lazily (the chrome chain and rings download it once the page is idle after its first view, `whenIdle`, and start once they come near view, `whenNearView`, both in `lib/lite.ts`; fetched only near view it arrived after people had scrolled past), are left out for visitors who save data or are on a slow connection, and where WebGL would be drawn on the CPU (`liteScenes`; `hardwareWebGL` asks once for a context with `failIfMajorPerformanceCaveat`, which software rendering refuses, so PageSpeed's GPU-less test machines see the CSS backgrounds), pause off screen, hold still with reduced motion and leave a CSS background when WebGL is missing. Each live scene is its own WebGL context, so keep them few: a dashboard has three (hero, chain, footer rings), the introduction two (hero, footer rings), and other pages at most one besides the footer; the mesh draws through one shared context into images. A canvas keeps one context for life and React mounts effects twice in development, so a scene that loses its context on cleanup creates its canvas inside the effect (as `LayersGradient.tsx` does) or creates the context only after an async import. The getlayers.ai shaders are verbatim; retint them through their `config` only. The ShaderGradient (`components/GradientBackdrop.tsx`, lazily loaded `GradientScene.tsx`) heads only the login and sign-up popups (`<Modal banner>`). `three` is pinned to 0.182.0 because from r183 three warns that `THREE.Clock` is deprecated, and @react-three/fiber 9.8.1 still creates one for every canvas.
- The backend is ESM with NodeNext resolution, so relative imports end in `.js`.
- Express 5 forwards thrown and rejected errors to the error handler. Throw `HttpError(status, message)` with a Korean message the user can read.
- The UI is a light theme after getlayers.ai's Stride in deep blue and silver, with slate grays instead of black. Design tokens are CSS variables on `:root` in `index.css`: `--point` is the deep blue point color and text on it uses `--on-point` (`--point-strong` for blue text on white); `--point-bright` (on white) and `--point-glow` (on deep blue) are the accent blues for the words a block turns on, such as a heading's accent line; copy uses `--ink`, `--ink-soft` and `--muted`; silver fills use `--fill`/`--fill-strong` or `--silver-gradient` with `--silver-ring`; hairlines are `--line` or the inset `--ring`; dark tiles use `--slate`; goals met and not yet met use `--goal-met` (deep blue) and `--goal-short` (silver), and the goal line over them `--goal-mark` (amber). Use the tokens rather than new hex values. A deep blue surface also sets `--surface-tone: dark`, which tells the header to show the light logo over it. Copy over a moving gradient sits on a navy shade or frosted navy glass; check its contrast against the live canvas when moving it. The PDF report pages keep their own print colors on `.pdf-export`.
- Pages open with `components/PageIntro.tsx` (eyebrow, title, actions). Main actions use `components/Pill.tsx` (`primary`, `white` on blue panels, `silver`, `outline`, `outline-light`); `.primary-button` (deep blue), `.cancel-button` (outlined) and `.detail-button` (silver) are the same pill shapes and turn white on blue banners. Brands and groups show as `components/WorkCard.tsx` and open as a profile (`pages/MatchDetailPage.tsx`): a card with an Antipode cover, the mark over its edge, who and where and the ways to get in touch, held beside two tabs on wide screens; 매칭 정보 (the match and one more figure, the score's parts as bars, then the introduction, SNS, facts and portfolio) and 파트너 후기 (`components/ReviewsSection.tsx`), both built from the tinted figure card and bars in `components/ProfileStats.tsx`. The dashboards are built from `MeetingHero`, `LogoMarquee`, `RevealStatement`, `StatsBento` and `JourneyChain`. The introduction reuses `MeetingHero` (a `lead` line instead of figures), `LogoMarquee` (brand industries and group fields, `data/industries.ts`), `RevealStatement`, the numbered `service-row`s and `FaqSection`; its copy says only what the service does. Its example cards show blurred pictures of member screens (`assets/examples/`, taken from the built app with Playwright) under the `예시 화면` mark. Visitors see member screens with the demo accounts' data as examples: the header's chip, `예시 화면` in the dashboards' hero, and parts that differ per account (the `가까운 순` tabs) blurred and inert under `components/DemoPreview.tsx` with login and sign-up. The counts beside the menu's pages (the header's pills and Menu) are only an account's own, so visitors get none. App's `visitor` stays false while a saved session is checked, so members never see these marks.
- Text is Pretendard Variable from the `pretendard` package, imported in `main.tsx`, in the weights of the `--weight-*` tokens only: Bold 700 (display headings, large numbers and emphasis), Medium 500 (copy), SemiBold 600 (labels, buttons, card titles, the menu's pages), ExtraBold 800 (badges, counts), Black 900 (the wordmark) and ExtraLight 200 only for decorative large text (the chain's aside). Don't use 100, 300 or 400. The PDF exports (the students' report, `ReportDocument`, and the brands' analytics, `AnalyticsDocument`) render A4 pages off screen and write in only the font files the pages loaded (`report/pdf.ts`). Animated headings use `RevealTitle`, `RevealWords` or `RevealStatement` (`components/RevealText.tsx`) with plain text, and `RevealTitle`'s `accent` colors one line in the accent blue; they wait for the intro loader (`lib/intro.ts`), and headings with a digit stay still.
- Motion lives in the "Motion" section of `index.css`: a `stagger` class on a list makes its items arrive one after another, `data-reveal` makes a block rise out of a blur when it scrolls into view (`lib/reveal.ts`, delay with `--reveal-delay`), `components/AnimatedNumber.tsx` counts numbers up on arrival, and `lib/ripple.ts` adds the press ripple. Keep the reduced-motion rule at the end of that section. Tailwind v4 is available, but the UI is styled through the classes in `index.css`.
- Analytics go through `lib/analytics.ts` (`contact_click` on a press of 제안하기 or 문의하기, `generate_lead` once the server accepts a proposal, `sign_up`); they do nothing until a GA4 ID is set in `.figma/make/site.json`, which adds Google's script and `/ga-init.js` (gtag's set-up as a file, since the Content-Security-Policy blocks inline scripts; `customScripts` in that file would be blocked the same way). Never put names, emails or message text in an event.
- Questions for the operators come from the FAQ page (`/api/inquiries`). Operators read and answer them on `/admin` (`pages/AdminPage.tsx`, in no menu), under the platform's figures (`GET /api/admin/stats`, `lib/stats.ts`: real members' counts beside the totals with the demo accounts and seed data), which calls `/api/admin` with the `ADMIN_TOKEN` environment value in the `X-Admin-Token` header (kept in sessionStorage for that tab only); those routes stay closed while it is unset. Question kinds are listed in both `backend/src/lib/validation.ts` and `frontend/src/data/inquiries.ts`.
- The terms of service and privacy policy (`/terms`, `/privacy`, `pages/LegalPage.tsx`) take their text from `frontend/src/data/legal.ts`. The privacy policy lists what the backend stores and how long; change it whenever stored data or retention changes. Both are drafts until an operator, contacts and a privacy officer are named.
- A forgotten password is reset through `/api/auth/password-reset/code` and `/api/auth/password-reset` (`modals/ResetPasswordModal.tsx`, opened from the login form). Reset codes are email codes with `purpose: "reset"` and share the sign-up codes' limits and carried-over guesses; a reset ends the account's other sessions.
- A handover moves the login email from 내 정보 (`modals/EmailChangeModal.tsx`): `POST /api/auth/email/code` with the password sends a code with `purpose: "change"`, tied to the asking account (shown as `devCode` like sign-up codes, never reset codes); `POST /api/auth/email` with it moves the account, ends its other sessions and tells the old address through `notify`. `GET /api/auth/export` hands an account everything it made or was sent (without its password hash or participants' passes and records), saved as a JSON file from 내 정보; when a new collection holds an account's data, add it there too.
- `saveDatabase()` also copies the data at most hourly, keeping the latest 24 (`backups` in `lib/storage.ts`): into `backups/` beside the data file, or the `uniconnect_backups` table with Postgres; a failed backup never fails the save. The privacy policy says backups may hold deleted data for up to 24 hours.
- Leaving is `DELETE /api/auth/account` with the password (`modals/LeaveModal.tsx` from 내 정보). `removeAccount` in `backend/src/routes/auth.ts` deletes everything the account made; when a new collection holds an account's data, add it there and to the privacy policy. The demo accounts cannot leave. A wrong password answers 400, not 401, which the app treats as an expired session.
- Verification codes go out through Resend from `backend/src/lib/mailer.ts` once `RESEND_API_KEY` and `MAIL_FROM` are set, and only to the server log before; a failed send answers 502. Sign-up codes (never reset codes) also come back as `devCode` only while `EXPOSE_EMAIL_CODES=true`, which `npm run dev` sets through `backend/dev.env` and nothing else does. The privacy policy names Resend as the mail processor. `notify` (`lib/notices.ts`) emails the other side about a new proposal or offer, an answer, or a message (once per run of unread messages), with a link when `SITE_URL` is set; it never fails the request, and never emails the shared demo accounts, whose addresses stand for no one. Tests swap `mailTransport.post` to see what would go out.
- Measurement is per event: `Database.measurements` holds one `Measurement` per event (counts, scans by hour, latest records, check-in `code` and goals), created with default goals when an event is first opened (`backend/src/lib/measurements.ts`). Reports are worked out from it in `buildReport` (reach = scans + `snsReach`, ROAS = visits × `averageSpend` ÷ the sponsorship's value). The side whose event it is edits the goals with `PUT /api/measurements/:eventId/goals` (`parseGoals`, `modals/GoalsModal.tsx`), opened from the agreement's 행사 목표 (`GoalsPanel` in `pages/AgreementPage.tsx`, App's `editGoals`) until the event begins; the measurement pages have no goals button and show an event still to come as 진행 전 (`measureState`), with dashes beside the goals and notes on what will show once it takes place (also in `MetricLogModal` through `startsOn`). The check-in page records through `/api/check-in/:code`: a scan answers a one-time `pass`, the coupon needs it once and answers a server-made coupon number. Visits are confirmed only from the store staff's own device (`/check-in/<code>/staff`, `checkin/StaffCheckInPage.tsx`, `POST /api/check-in/:code/staff/visits`) with that number and the event's 4-digit `staffPin` (only the owner sees it, in the report); wrong PINs are limited per address (10) and per event (30) per 15 minutes. Scans and coupons count only on the event's days and the day after, visits until 7 days after that (`checkInWindow`, `assertOpen`), except on the demo accounts' events so visitors can try the flow; `prunePasses` drops the records an event no longer needs on each start, and an event keeps at most `passLimit` of them. `hourlyScans` are by Korean day and hour. The participant's page polls `/passes/:pass` to show the visit. Brands measure their own campaigns the same way (`components/CampaignMeasurement.tsx` at the end of 성과 분석; visitors preview with `?role=브랜드`). The app picks the event to show with `defaultMeasurement` (`frontend/src/lib/measurements.ts`), and pages get its `metrics` and `report` as before. Accepting a proposal (a request or an offer) records one of the brand's sponsorships (`recordSponsorship` in `backend/src/lib/sponsorships.ts`), linked by `eventId` to a student event. `/api/analytics` shows those whose day has come, and one with an `eventId` takes its coupons, visits, estimated sales, value and ROAS goal from that event's measurement.
- Requests that can be guessed or flooded (login failures, email codes, admin token failures, check-in records, Kakao shop searches) are counted per address with `createRateLimit` from `backend/src/lib/rateLimit.ts` and answer 429 past their limit. The counts live in memory, per copy of the API on Vercel; set `TRUST_PROXY` to the number of proxies (usually 1, the default on Vercel) behind a proxy so `req.ip` is the visitor; `true` lets callers forge their address and the server warns about it. Login, leaving and password change count the attempt with `take` before the slow password check. Tests clear them before each case with `clearRateLimits`.
- Sessions keep only `tokenHash` (sha256 of the browser's token, `hashToken` in `middleware/session.ts`). Sign-up needs `over14: true` besides `agreedToTerms`. `POST /api/auth/password` changes the password with the current one and ends the account's other sessions. `app.ts` sets the security headers, including a Content-Security-Policy that allows only this site's scripts (plus Google Tag Manager) and inline styles; a new outside script, font or API needs adding there.
- Each accepted proposal (request or offer) has an agreement (협찬 약속서, `routes/agreements.ts`, `lib/agreements.ts`, `pages/AgreementPage.tsx`, the list `pages/AgreementsPage.tsx` at `/agreements`): `Database.agreements` keyed by the proposal's id, made with the usual items the first time either side opens it. Its view carries the event (`event`: id, the side whose it is (the group for a request, the brand for an offer's campaign) and whether it has begun, `sponsoredEvent`) and the goals both sides read (`goals`: expected audience and targets, never PINs or coupons); opening it makes the event's measurement as opening the event would. Either side edits the items, which clears both confirmations; each side confirms, and marks done and proves only its own items with links and photos. Photos are resized in the browser (`photoFromFile` in `lib/image.ts`) to fit the 300kb request limit, kept through `lib/photos.ts`, on disk in `uploads/<id>/` beside the data file or in the `uniconnect_photos` table with Postgres (not in the hourly backups), and served only to the two sides, so the page fetches them with the token (`requestBlob`). When an account leaves, `removeAccount` drops agreements whose proposal went (`dropOrphanAgreements`) and the route removes their photos after saving.
- After a sponsorship's event day, each side can review the other from the agreement page (`routes/reviews.ts`, `lib/reviews.ts`, `ReviewPanel` in `pages/AgreementPage.tsx`): `Database.reviews`, one per side per accepted proposal (`${proposalId}:${side}`), with stars, up to three tags from `reviewTags` (`validation.ts` and `data/reviews.ts`, by the side reviewed; `lists.sync.test.ts` checks) and a comment of 300 characters at most. Reviews are public on the reviewed listing's detail page (its 파트너 후기 tab, `components/ReviewsSection.tsx`: the average, the share that picked 다시 함께하고 싶어요, each other tag's share from the summary's count of every tag, the latest review and the rest on request) and as `rating`/`reviewCount` worked out in `browse()` (the star chip on `WorkCard`); they never change the match score. The shared demo accounts can't write them. `seedReviews()` adds three past ones for the demo (`stored.reviews ??=`); `removeAccount` deletes the reviews an account wrote and those about it.
- Dates that are near: `sendReminders` (`backend/src/lib/reminders.ts`, run by `index.ts` at start and hourly, never by `createApp`; on Vercel by Vercel Cron once a day through `GET /api/cron/reminders`, `routes/cron.ts`, which needs `CRON_SECRET` as a bearer token and is closed without it) emails each account once per event, and a brand once per sponsored day, three days ahead or nearer (`remindedAt` on the event or sponsorship), never the demo accounts; the bell lists the same days first (`soonNotices` in `lib/notifications.ts`). `캘린더에 추가` on the calendar pages saves an iCalendar file made in the browser (`lib/ics.ts`, all-day entries with a reminder at 9 a.m. the day before, through `saveFile` in `lib/download.ts`). The built app is installable: `public/manifest.webmanifest`, `public/icons/`, and `public/sw.js`, registered by `main.tsx` only in production, which never caches `/api/` (answers are personal, and Kakao's may not be kept), fetches pages from the network with the last shell kept for offline, and keeps the newest 80 hashed assets. Push notifications need VAPID keys and are not set up. The site opens as a web page first:

- An event with an accepted proposal or a recorded sponsorship cannot be deleted (409, `isSponsored` in `lib/sponsorships.ts`); deleting one withdraws its waiting proposals on both sides, and accepting a proposal about a deleted event answers 409. When an account leaves, `freezeSponsorships` copies the live figures into its sponsors' records before its measurements go. Each sponsor of an event has its own share on the measurement (`Measurement.sponsors`, kept in step by `syncSponsors` in `lib/measurements.ts` when a sponsorship is recorded, a measurement is created or the data loads): its coupon, staff PIN (unique per event), coupon and visit counts and value (`shareValue`: the whole value for one sponsor, else what the group set in the goals form, adding up to the event's value, or an even split). Participants take each sponsor's coupon (`couponId` on `POST /api/check-in/:code/coupons`, passes keep them under `sponsors`), a store's PIN confirms only its own coupons, and `/api/analytics` reads a sponsorship's figures from its share. The event's first sponsor, when it is the only one, takes over the event's coupon, PIN, counts and coupon numbers. `metrics` stays the whole event's for the group's report, which lists the shares as `report.sponsors`.
- When a write fails, `saveDatabase()` puts the data in memory back to what was last written and rejects with a 503 ("되돌렸어요") for that caller and for writes queued behind it, so a failed request leaves nothing behind and can be retried; later saves still run. When another copy of the API wrote first, the newer data comes in as well, and reading the data anew also turns away writes queued before it. Every write route mutates memory and then awaits `saveDatabase()`, and nothing else should change the data without saving. Look up request input in plain lookup objects with `Object.hasOwn`, so names like `constructor` are not found.
