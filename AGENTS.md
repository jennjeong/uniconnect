# uniconnect

Sponsorship matching prototype that connects student groups (학생단체) with brands (브랜드). It is a pnpm workspace with a React frontend and an Express API. The UI copy is Korean.

## Commands

Run these from the repo root:

- `corepack pnpm@10.34.3 install` installs every workspace package.
- `npm run dev` starts the API on http://localhost:4000 and Vite on http://localhost:8443. Vite proxies `/api` to the API. The API reads `backend/dev.env` and, when it exists, `backend/.env.local`, the git-ignored home of private keys such as `KAKAO_REST_API_KEY`; never write a key into a tracked file.
- `npm run typecheck` runs tsc for the backend and the frontend.
- `npm test` runs the backend tests (`node:test` through tsx: the API in `app.test.ts`, and the Postgres store in `store.postgres.test.ts` on PGlite, an in-process Postgres, in its own process), then the frontend unit tests (vitest, `frontend/src/**/*.test.ts`, configured in `frontend/vitest.config.ts` without the app's Vite plugins). `frontend/src/lib/appPaths.sync.test.ts` checks `backend/src/lib/appPaths.ts` against `route.ts`.
- `npm run e2e` (after `npm run build`) runs the Playwright browser tests in `e2e/` against the built app on port 4300 with a fresh temp data file (and `CODES_PER_CLIENT=200`, as every test signs up from the same address), in the installed Chrome (`channel: "chrome"`, no browser download): the main flows and axe accessibility checks (WCAG 2.1 A/AA; critical and serious problems fail).
- GitHub Actions (`.github/workflows/ci.yml`) runs install, typecheck, test, build and e2e on every push to main and every pull request.
- `.github/workflows/neon-preview-cleanup.yml` runs when a pull request closes. It deletes that PR's Neon preview database branch, `preview/<branch>`, through the Neon API with the `NEON_API_KEY` secret. It skips the default and protected branches, and passes with a notice when there is no key or no such branch.
  - Why it exists: Vercel's Neon integration (`neon-lime-lever`) makes one such branch per previewed Git branch, and keeps it until that branch's last preview deployment is deleted.
  - Neon's free plan holds 10 branches. Once they are used up, every preview fails at "Provisioning Integrations" with "Branch limit reached".
- `npm run build`, then `npm start`, builds both packages and serves the API plus the built frontend from Express.

## Project Structure

- `frontend/src/App.tsx` holds the app state and the API calls, and switches between pages and modals for the current role.
- `frontend/src/api/` has the fetch wrapper with the Bearer token (`client.ts`) and one function per endpoint (`index.ts`).
- `frontend/src/pages/`, `modals/`, `layout/` and `components/` contain the UI. `data/`, `lib/` and `hooks/` contain constants and helpers.
- `frontend/src/layout/Header.tsx` is the fixed header: the logo on its own, then floating pills for the role's menu on wide screens, the next event, account buttons and Menu (on the introduction a visitor gets its sections and 회원가입 instead of the menu; on a member screen shown to a visitor, a `예시 화면` chip sits by the logo) (registering is on the 내 행사 and 행사 일정 calendars and in Menu). The logo switches to its light version (`assets/brand/uniconnect_horizontal_reversed.svg`) over deep blue surfaces. `NavMenu.tsx` is the full-screen silver menu behind Menu and `Footer.tsx` the footer: the site's links, headed on the introduction (sign up, get the app) and the dashboard by a deep blue mesh card with linked chrome rings and the call to register (the whole footer is left out of a conversation).
- `frontend/src/scenes/` holds the WebGL effects: getlayers.ai's Antipode gradient (the introduction's and dashboards' hero, detail banners) and Interference gradient (reports, measurement, analytics), run by `LayersGradient.tsx` from `shaders.ts`; Stride's mesh gradient, drawn once into an image (`MeshBackdrop.tsx`); and its chrome chain and rings (`ChromeScene.tsx`, `chromeModels.ts`).
- `frontend/src/index.css` is the single global stylesheet. Components use its class names, so a renamed class must change in both places.
- `backend/src/routes/` has one Express router per resource.
- `backend/src/data/seed.ts` holds the demo accounts and data.
- `backend/src/store.ts` holds the data in memory as one document and writes it through `lib/storage.ts`: to `backend/data/db.json` (gitignored; delete it to reseed), or, when `DATABASE_URL` is set, to Postgres (`lib/sql.ts`: Neon's HTTP driver, or a `useSql` test database), which every copy of the API shares. `ensureTables` makes the tables on first use and runs a `create table` once more when a copy starting at the same moment made it first (Postgres answers 23505 or 42P07 then). Each write carries the version it builds on (`StaleWrite` when another copy wrote first), and with shared storage each `/api` request first calls `refreshDatabase()`, which reads the data again when the stored version moved on (at most every `freshness.everyMs`). Agreement photos go through `lib/photos.ts` (files under `uploads/`, or rows in Postgres).
- Vercel runs the built frontend as static files and the API as one function, `api/index.mjs` → `backend/src/vercel.ts` (it loads the data on each copy's first request through `createApp`'s `loaded`); `vercel.json` holds the build, the routes (the app's addresses, as in `appPaths.ts`, get `index.html`; anything else gets `404.html`, a copy of it the frontend build makes, with a 404 status; the rewrites match strictly, so `trailingSlash: false` first redirects an address ending in a slash to the one without it), the region (`sin1`, beside the Neon database) and the security headers, which must match `app.ts` (a test compares them). Background work after a response needs `waitUntil` from `@vercel/functions`, as `notify` does; nothing may rely on timers or files lasting there.

## Conventions

- The UI is in Korean or English (`frontend/src/i18n`): the choice made in 내 정보's 언어 row or with the footer's switch, else Korean when the browser's first language is Korean and English for any other (Korean in unit tests, which have no window). Copy is written in Korean and wrapped in `t("…", values)`; the Korean is the key and its English lives in `i18n/en/<area>.ts` (`{name}` parts filled from `values`). Never translate values used in logic (roles, NavLabels, statuses, sponsor kinds, tab values): show them with `t(value)`, and keep their English in `i18n/en/common.ts`. `i18n/coverage.test.ts` fails for a `t()` sentence without English, `i18n/lists.test.ts` for a listed value. Dates and money follow the language (`lib/date.ts`, `formatWon`, `fullWon`, `manWon`/`wonUnit`). The client sends the language as `Accept-Language`; the server still writes its messages in Korean and answers them in English through `backend/src/lib/i18n.ts` and `backend/src/i18n/en.ts` (`{name}` patterns for messages with a value). The legal pages show an English translation with a note that the Korean original prevails. Emails are in the account's `language` (set at sign-up from the page's language, and by the app whenever the one it shows differs, through `PUT /api/auth/preferences`): `notify` and the code emails put each Korean line through `translate`, so a new email line needs its English (a `{name}` pattern when it has a value) in `backend/src/i18n/en.ts`.

- `frontend/src/types.ts` mirrors the API shapes in `backend/src/types.ts`.
- Account types and sponsor types are listed in both `backend/src/lib/validation.ts` and the frontend (`data/roles.ts`, `data/sponsorTypes.ts`). Change them together. The frontend shows account types in groups (`accountTypeGroups`, flattening to the same order), and `catalog.ts` files each under one of the eight industries the match and the marks use; a renamed type goes in `renamedAccountTypes`, which the store applies on load. Sign-up asks for the person running the account (`contact`: name, position, a mobile number stored as 010-1234-5678 by `parseContact`), changed from 내 정보 (`PUT /api/auth/contact`, `modals/ContactModal.tsx`) and shown to no one but the two sides of an accepted proposal, on its agreement; the privacy policy says so. The position is picked from `positionHints` (`components/PositionField.tsx`, a select with 직접 입력 for any other), kept in Korean and shown through `t()`. A new password (sign-up, reset, change) is 8 to 64 characters with an English letter, a number and a symbol and no spaces: `checkPassword` in `validation.ts` and `lib/password.ts` with `components/PasswordRules.tsx` under the boxes (`lists.sync.test.ts` checks they agree). The same goes for profile fact labels and SNS platforms (`validation.ts` and `data/profile.ts`) and question kinds (`data/inquiries.ts`); `frontend/src/lib/lists.sync.test.ts` fails when they differ.
- Proposals go both ways through `POST /api/proposals`: a student group's reaches a brand with an account as a `SponsorRequest` (`/api/requests`, the brand's 받은 제안), a brand's reaches a group with an account as a `SponsorOffer` (`/api/offers`, the group's 받은 협찬, `pages/OffersPage.tsx`). Both inboxes share `components/RequestProgress.tsx` and the `request-*` classes, and `/api/proposals` answers each side's statuses and `sent`, the account's own requests or offers (partner, its event, what it offered, status), which both inboxes list under 검토 중 beside the received ones with 제안 취소 (`components/SentProposals.tsx`). A proposal to a partner with an account is about an event or campaign of the sender's that has not ended, picked in `modals/ProposeModal.tsx` (`eventId`, the next one when left out; another account's is 404, an ended one 409) with the sender's note (`message`, 300 characters at most, the usual greeting when empty, shown on both inboxes' cards and in the email), and needs one (409 otherwise), so an accepted one always becomes a dated sponsorship; one waiting for an answer is not sent twice, an accepted one can be sent again only about a later event, and withdrawing then takes back only the waiting one. One still waiting once its event has ended is closed (`마감`, `statusOf` in `lib/proposals.ts`, worked out wherever it is shown or answered and never stored): it can't be answered (409), both inboxes show it under its own 마감 tab, and it doesn't hold back a new proposal to the same partner.
- A listing's `logo` is a PNG, JPEG or WebP data URL of about 100KB at most, resized in the browser (`lib/image.ts`) and checked in `routes/profile.ts` (left out keeps it, null removes it); it lives in db.json for now.
- The brand and group catalogs are editable listings: each account's own listing is linked by `brandId`/`groupId` and edited from 내 정보. Recommended matches are the other catalog's top three, worked out in `backend/src/lib/catalog.ts`.
- Members (accounts that signed up) see only members' listings. The seed catalog and the demo accounts' listings are the examples, seen by visitors and by the shared demo accounts, which stay as trial logins; the login popup logs into either with one press (`data/demo.ts`, kept equal to the seed by `lib/lists.sync.test.ts`). The two never meet: `shownTo`/`shownCatalog` in `lib/catalog.ts` decide the catalogs and matches, proposals and conversations accept only a partner the account sees (404 otherwise), a member's proposal list and conversations leave out the examples, 가까운 순 shows a shop as its brand only to those who see that brand, and the demo group can't invite shops (403), as an invitation reaches a real owner. A member's empty catalog says so with what to do meanwhile (`components/CatalogEmpty.tsx`, once App's `catalogReady` says it has loaded), and 추천's heading stops claiming it found any. App empties every list in the same render the viewer changes (`listsFor`; an effect would draw the last viewer's data for a frame), so the examples never flash after logging in. The bell lists only what exists (no recommendation notice without matches). Each notice lists its `parts` (each offer, match or near day it counts) and is unread while one isn't in the account's `readNotices`; opening it or 모두 읽음 saves the parts on show through `PUT /api/auth/notices`, replacing the list, so every device shows the same dot and the list stays short. The dot shows only while a notice is unread. Each listing's `score` (55–98), `reasons` and `scoreParts` (each part as a share of its best, 0 to 1, with a short label the detail page shows as a bar; the labels' English is listed in `i18n/lists.test.ts`) are worked out for the account browsing, or the demo account of that side for visitors, in `backend/src/lib/matchScore.ts`: industry fit 35, shared tag words 15, track record 20 (a brand's sponsorships, a group's event size), sponsored together before 15, ready to answer 15. The `score` stored on a listing is not used.
- Distances on the catalogs (단체 찾기's 가까운 순 tab, the pin chip on `WorkCard`) are straight-line km between a group's campus and a brand's store, worked out in `browse()` with `lib/geo.ts`. A campus comes from the table in `backend/src/data/campuses.ts` (each university's own feature in OpenStreetMap, with its road address beside it; add schools the same way), found by the account's email domain, else the school name. A brand's store is `location` on its listing, written as `address` from 내 정보 and placed on the map through OpenStreetMap's Nominatim (`lib/geocode.ts`) only when `NOMINATIM_URL` is set (`backend/dev.env` sets the public server; it takes one request a second, so lookups are spaced 1.1s apart, and its ODbL data may be kept with the `Map data © OpenStreetMap contributors` credit in the footer). Never store coordinates from Kakao's or VWorld's geocoders: both allow live use only. Catalog version 4 dropped the Kakao coordinates saved before. Without coordinates there is no distance, and the save notice and the edit form say so. Tests and the e2e server run without a geocoder or a Kakao key. Distance never changes the match score. The privacy policy names the OpenStreetMap Foundation for this.
- The 가까운 순 tab on 추천 매칭 (`components/NearbyPlaces.tsx`) lists real shops around the student group's campus from Kakao Local's category search (visitors get made-up shops around the demo group's campus instead, `data/exampleShops.ts` through `exampleNearby`, marked `example`, with no map page or phone, and Kakao isn't asked), as the other tabs' cards (WorkCard's classes) with 협약 전 where a partner's card offers a proposal: every kind merged at first (`category=all`, the nearest 30), or one kind. A chain's branch shows its logo (`lib/franchises.ts` matches the name's start, `data/franchises.ts` holds the PNGs from Wikimedia Commons in `assets/franchises/`: public domain as artwork, still trademarks, so add a chain only with its logo's licence checked), any other shop its name's first letter; `GET /api/places` in `routes/places.ts` with `lib/places.ts`, the kinds listed in `validation.ts` and `data/places.ts`. Kakao allows Local API results only as live answers shown on screen: never store or cache them (only a place's ID and Kakao Map URL may be kept), so each look asks Kakao again and the route is rate-limited per address instead, counting each kind asked. Tests swap `placeSearch.search`. Each shop comes with its point, used only to draw `components/PlaceMap.tsx` (the 목록 · 지도 switch: a sketch around the campus, scaled to the farthest shop by `lib/placeMap.ts`, with stacked dots spread apart), never kept. A 협약 전 shop can be invited (`routes/invites.ts`, `modals/InviteShopModal.tsx`): a `ShopInvite` in `Database.invites` keeps only the place's ID and Kakao Map URL, and its page `/invite/<code>` (`pages/InvitePage.tsx`, the brand side for visitors) lets the owner sign up as a brand and link the shop with one press, which lists the brand at once with `kakaoPlaceId` on its listing (one shop per brand, one brand per shop) and emails the groups that invited it; 가까운 순 then shows that shop as the brand, with a proposal.
- The catalogs can be searched (`components/CatalogSearch.tsx`, `matchesQuery` in `lib/search.ts`: every word typed, in name, kind, offer, tags, school or event), and 단체 찾기 also filters by the next event's size and month and by school (`matchesGroupFilters`). Search and filters apply to whichever tab is open and stay when the tab changes.
- Student groups and brands have separate menus and pages (`data/navigation.ts`). A feature for one side gets its own page rather than a role branch inside the other side's page.
- Every screen is a `View` with its own address (`lib/route.ts`), title and description (`lib/pageMeta.ts`). `/` is the introduction for visitors (`home`, `pages/LandingPage.tsx`) and the dashboard lives at `/dashboard`; a member opening `/` goes on to the dashboard, and nothing shows there while a saved session is checked. History entries keep their view, and `entryView` drops one that no longer fits its address (kept from before the dashboard moved). An address no screen has becomes a `missing` view, the 404 page; `backend/src/lib/appPaths.ts` lists the same addresses so the server answers the rest with a real 404, and `vercel.json`'s rewrites list them again for Vercel, so change the three together (`appPaths.sync.test.ts` checks). Screens for one account or one link, and the dashboard, carry `noindex` in their meta (`keepOutOfSearch`, also called by the check-in pages); the rest are open to search engines (`robots.index` in `frontend/.figma/make/site.json`, `public/robots.txt`); `/sitemap.xml` is made at build from site.json's `url` and `sitemap` (`lib/sitemap.ts` through vite.config.ts; `lib/sitemap.test.ts` checks each page is a real, indexable screen and that robots.txt's `Sitemap:` matches), and site.json's `verification` codes (Google, Naver) become meta tags once set, and `public/llms.txt` describes the site for AI agents. Change screens through App's `go` and `goBack`, never by setting state directly, so the browser's back and forward buttons and swipe gestures keep working. `lib/swipe.ts` adds swiping anywhere on the page through those entries (one finger, or two on a trackpad: left to right goes back, right to left forward), leaving swipes from the screen edge to the browser; `go` tells it through `noteHistoryEnd` how far forward history reaches, and the screen a swipe brings slides in from that side (`data-swiped` in the "Motion" section).
- Popups go inside `<Presence>` (`components/Presence.tsx`) so they animate closed however they are closed.
- Password, PIN and token boxes are `components/PasswordField.tsx`: the label with its input and an eye button inside the box that shows what was typed (`aria-pressed`, one fixed name such as 비밀번호 보기, which must not contain the field's label, or `getByLabel` finds both). A new one uses it too.
- The scenes load three.js lazily (the chrome chain and rings download it once the page is idle after its first view, `whenIdle`, and start once they come near view, `whenNearView`, both in `lib/lite.ts`; fetched only near view it arrived after people had scrolled past), are left out for visitors who save data or are on a slow connection, and where WebGL would be drawn on the CPU (`liteScenes`; `hardwareWebGL` asks once for a context with `failIfMajorPerformanceCaveat`, which software rendering refuses, so PageSpeed's GPU-less test machines see the CSS backgrounds), pause off screen, hold still with reduced motion and leave a CSS background when WebGL is missing. Each live scene is its own WebGL context, so keep them few: a dashboard has three (hero, chain, footer rings), the introduction two (hero, footer rings), and other pages at most one besides the footer; the mesh draws through one shared context into images. A canvas keeps one context for life and React mounts effects twice in development, so a scene that loses its context on cleanup creates its canvas inside the effect (as `LayersGradient.tsx` does) or creates the context only after an async import. The getlayers.ai shaders are verbatim; retint them through their `config` only. The ShaderGradient (`components/GradientBackdrop.tsx`, lazily loaded `GradientScene.tsx`) heads only the login and sign-up popups (`<Modal banner>`). `three` is pinned to 0.182.0 because from r183 three warns that `THREE.Clock` is deprecated, and @react-three/fiber 9.8.1 still creates one for every canvas.
- The backend is ESM with NodeNext resolution, so relative imports end in `.js`.
- Express 5 forwards thrown and rejected errors to the error handler. Throw `HttpError(status, message)` with a Korean message the user can read.
- The UI is a light theme after getlayers.ai's Stride in deep blue and silver, with slate grays instead of black. Design tokens are CSS variables on `:root` in `index.css`: `--point` is the deep blue point color and text on it uses `--on-point` (`--point-strong` for blue text on white); `--point-bright` (on white) and `--point-glow` (on deep blue) are the accent blues for the words a block turns on, such as a heading's accent line; copy uses `--ink`, `--ink-soft` and `--muted`; silver fills use `--fill`/`--fill-strong` or `--silver-gradient` with `--silver-ring`; hairlines are `--line` or the inset `--ring`; dark tiles use `--slate`; goals met and not yet met use `--goal-met` (deep blue) and `--goal-short` (silver), and the goal line over them `--goal-mark` (amber). Use the tokens rather than new hex values. A deep blue surface also sets `--surface-tone: dark`, which tells the header to show the light logo over it. Copy over a moving gradient sits on a navy shade or frosted navy glass; check its contrast against the live canvas when moving it. The PDF report pages keep their own print colors on `.pdf-export`.
- Pages open with `components/PageIntro.tsx` (eyebrow, title, actions). Main actions use `components/Pill.tsx` (`primary`, `white` on blue panels, `silver`, `outline`, `outline-light`); `.primary-button` (deep blue), `.cancel-button` (outlined) and `.detail-button` (silver) are the same pill shapes and turn white on blue banners. Brands and groups show as `components/WorkCard.tsx` and open as a profile (`pages/MatchDetailPage.tsx`): a card with an Antipode cover, the mark over its edge, who and where and the ways to get in touch, held beside two tabs on wide screens; 매칭 정보 (the match and one more figure, the score's parts as bars, then the introduction, SNS, facts and portfolio) and 파트너 후기 (`components/ReviewsSection.tsx`), both built from the tinted figure card and bars in `components/ProfileStats.tsx`. The dashboards are built from `MeetingHero`, `LogoMarquee`, `RevealStatement`, `StatsBento` and `JourneyChain`. The introduction reuses `MeetingHero` (a `lead` line instead of figures), `LogoMarquee` (brand industries and group fields, `data/industries.ts`), `RevealStatement`, the numbered `service-row`s and `FaqSection`; its copy says only what the service does. Its example cards show pictures of member screens (`assets/examples/`, taken from the built app with Playwright), their made-up brands and groups readable, under the `예시 화면` mark. Visitors see member screens with the demo accounts' data as examples: the header's chip, `예시 화면` in the dashboards' hero, and parts that differ per account (the `가까운 순` tabs) in full with made-up shops or the example groups, under the note from `components/DemoPreview.tsx` that says so, with login and sign-up. The counts beside the menu's pages (the header's pills and Menu) are only an account's own, so visitors get none. App's `visitor` stays false while a saved session is checked, so members never see these marks.
- Text is Pretendard Variable from the `pretendard` package, imported in `main.tsx`, in the weights of the `--weight-*` tokens only: Bold 700 (display headings, large numbers and emphasis), Medium 500 (copy), SemiBold 600 (labels, buttons, card titles, the menu's pages), ExtraBold 800 (badges, counts), Black 900 (the wordmark) and ExtraLight 200 only for decorative large text (the chain's aside). Don't use 100, 300 or 400. The report and the analytics also download as CSV (`lib/csv.ts`, made on the page with `saveFile`: UTF-8 with a BOM and CRLF, headers in the language shown, and text starting with `=`, `+`, `-` or `@` prefixed with `'` against CSV injection; build its rows from the same helpers the pages use, such as `reportKpis` and `roasOf`). The PDF exports (the students' report, `ReportDocument`, and the brands' analytics, `AnalyticsDocument`) render A4 pages off screen and write in only the font files the pages loaded (`report/pdf.ts`). Animated headings use `RevealTitle`, `RevealWords` or `RevealStatement` (`components/RevealText.tsx`) with plain text, and `RevealTitle`'s `accent` colors one line in the accent blue; they wait for the intro loader (`lib/intro.ts`), and headings with a digit stay still.
- Motion lives in the "Motion" section of `index.css`: a `stagger` class on a list makes its items arrive one after another, `data-reveal` makes a block rise out of a blur when it scrolls into view (`lib/reveal.ts`, delay with `--reveal-delay`), `components/AnimatedNumber.tsx` counts numbers up on arrival, and `lib/ripple.ts` adds the press ripple. Keep the reduced-motion rule at the end of that section. Tailwind v4 is available, but the UI is styled through the classes in `index.css`.
- Analytics go through `lib/analytics.ts` (`contact_click` on a press of 제안하기 or 문의하기, `generate_lead` once the server accepts a proposal, `sign_up`); they do nothing until a GA4 ID is set in `.figma/make/site.json`, which adds Google's script and `/ga-init.js` (gtag's set-up as a file, since the Content-Security-Policy blocks inline scripts; `customScripts` in that file would be blocked the same way). Never put names, emails or message text in an event.
- Questions for the operators come from the FAQ page (`/api/inquiries`). Operators read and answer them on `/admin` (`pages/AdminPage.tsx`, in no menu), under the platform's figures (`GET /api/admin/stats`, `lib/stats.ts`: real members' counts beside the totals with the demo accounts and seed data), which calls `/api/admin` with the `ADMIN_TOKEN` environment value in the `X-Admin-Token` header (kept in sessionStorage for that tab only); those routes stay closed while it is unset. Question kinds are listed in both `backend/src/lib/validation.ts` and `frontend/src/data/inquiries.ts`. A new or changed answer is emailed to the asker through `notify` and shows on the bell (`answerNotices` in `lib/notifications.ts`, whose `faq` notice opens the help center's questions, `AskModal`) until the asker sees it there (`POST /api/inquiries/read` sets `answerReadAt`).
- The terms of service and privacy policy (`/terms`, `/privacy`, `pages/LegalPage.tsx`) take their text from `frontend/src/data/legal.ts`. The privacy policy lists what the backend stores and how long; change it whenever stored data or retention changes. Both are drafts until an operator, contacts and a privacy officer are named.
- A forgotten password is reset through `/api/auth/password-reset/code` and `/api/auth/password-reset` (`modals/ResetPasswordModal.tsx`, opened from the login form). Reset codes are email codes with `purpose: "reset"` and share the sign-up codes' limits and carried-over guesses; a reset ends the account's other sessions.
- A handover moves the login email from 내 정보 (`modals/EmailChangeModal.tsx`): `POST /api/auth/email/code` with the password sends a code with `purpose: "change"`, tied to the asking account (shown as `devCode` like sign-up codes, never reset codes); `POST /api/auth/email` with it moves the account, ends its other sessions and tells the old address through `notify`. `GET /api/auth/export` hands an account everything it made or was sent (without its password hash or participants' passes and records), saved as a JSON file from 내 정보; when a new collection holds an account's data, add it there too.
- `saveDatabase()` also copies the data at most hourly, keeping the latest 24 (`backups` in `lib/storage.ts`): into `backups/` beside the data file, or the `uniconnect_backups` table with Postgres; a failed backup never fails the save. The privacy policy says backups may hold deleted data for up to 24 hours.
- Errors are kept for the operators (`lib/errorLog.ts`): the error handler in `app.ts` records 5xx answers (unexpected errors with the first frames of their stack), and the built app reports errors the page didn't catch (`lib/errorReports.ts`, five a page, `POST /api/errors`, limited per address), each with its message, where, the path without its query and when, never names, emails or typed text.
