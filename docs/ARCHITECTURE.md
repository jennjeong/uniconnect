# uniconnect

Sponsorship matching prototype that connects student groups (학생단체) with brands (브랜드). It is a pnpm workspace with a React frontend and an Express API. The UI copy is Korean.

## Commands

Run these from the repo root:

- `corepack pnpm@10.34.3 install` installs every workspace package.
- `npm run dev` starts the API on http://localhost:4000 and Vite on http://localhost:8443. Vite proxies `/api` to the API. The API reads `backend/dev.env` and, when it exists, `backend/.env.local`, the git-ignored home of private keys such as `KAKAO_REST_API_KEY` and the Toss test keys; `backend/.env.example` lists every such key with empty values, to copy to `.env.local` (`.gitignore` lets only it through). Never write a key into a tracked file, the example included.
- `npm run typecheck` runs tsc for the backend and the frontend.
- `npm test` runs the backend tests (`node:test` through tsx: the API in `app.test.ts`, and the Postgres store in `store.postgres.test.ts` on PGlite, an in-process Postgres, in its own process), then the frontend unit tests (vitest, `frontend/src/**/*.test.ts`, configured in `frontend/vitest.config.ts` without the app's Vite plugins). `frontend/src/lib/appPaths.sync.test.ts` checks `backend/src/lib/appPaths.ts` against `route.ts`.
- `npm run e2e` (after `npm run build`) runs the Playwright browser tests in `e2e/` against the built app on port 4300 with a fresh temp data file (and `CODES_PER_CLIENT=200`, as every test signs up from the same address), in the installed Chrome (`channel: "chrome"`, no browser download): the main flows and axe accessibility checks (WCAG 2.1 A/AA; critical and serious problems fail).
- GitHub Actions (`.github/workflows/ci.yml`) runs install, typecheck, test, build and e2e on every push to main and every pull request.
- `.github/workflows/neon-preview-cleanup.yml` runs when a pull request closes. It deletes that PR's Neon preview database branch, `preview/<branch>`, through the Neon API with the `NEON_API_KEY` secret. It skips the default and protected branches, and passes with a notice when there is no key or no such branch.
  - Why it exists: Vercel's Neon integration (`neon-lime-lever`) makes one such branch per previewed Git branch, and keeps it until that branch's last preview deployment is deleted.
  - Neon's free plan holds 10 branches. Once they are used up, every preview fails at "Provisioning Integrations" with "Branch limit reached".
- `npm run build`, then `npm start`, builds both packages and serves the API plus the built frontend from Express.

## Project Structure

- `frontend/src/App.tsx` holds the app state and the API calls, and switches between pages and modals for the current role. Only the introduction, the dashboards, the 404 page and the login and sign-up popups are in the first download; every other page, popup and the PDF exports are `lazy` chunks that load the first time they open (`<Suspense>` with `PageLoading` for pages, nothing for popups), so a new page or popup is added the same way.
- `frontend/src/api/` has the fetch wrapper with the Bearer token (`client.ts`) and one function per endpoint (`index.ts`).
- `frontend/src/pages/`, `modals/`, `layout/` and `components/` contain the UI. `data/`, `lib/` and `hooks/` contain constants and helpers.
- `frontend/src/layout/Header.tsx` is the fixed header: the logo on its own, then floating pills for the role's menu on wide screens, the next event, account buttons (the account's circle drops a small panel like the bell's, `layout/AccountPanel.tsx`: who is logged in, 내 정보 and 로그아웃; the two panels close each other, through `hooks/useDismiss.ts`) and Menu (on the introduction a visitor gets its sections and 회원가입 instead of the menu; on a member screen shown to a visitor, a `예시 화면` chip sits by the logo) (registering is on the 내 행사 and 행사 일정 calendars and in Menu). The logo switches to its light version (`assets/brand/uniconnect_horizontal_reversed.svg`) over deep blue surfaces. `NavMenu.tsx` is the full-screen silver menu behind Menu and `Footer.tsx` the footer: the site's links, headed on the introduction (sign up, get the app) and the dashboard by a deep blue mesh card with linked chrome rings and the call to register (the whole footer is left out of a conversation).
- `frontend/src/scenes/` holds the WebGL effects: getlayers.ai's Antipode gradient (the introduction's and dashboards' hero, detail banners) and Interference gradient (reports, measurement, analytics), run by `LayersGradient.tsx` from `shaders.ts`; Stride's mesh gradient, drawn once into an image (`MeshBackdrop.tsx`); and its chrome chain and rings (`ChromeScene.tsx`, `chromeModels.ts`).
- `frontend/src/index.css` is the single global stylesheet. Components use its class names, so a renamed class must change in both places.
- `backend/src/routes/` has one Express router per resource.
- `backend/src/data/seed.ts` holds the demo accounts and data.
- `backend/src/store.ts` holds the data in memory as one document and writes it through `lib/storage.ts`: to `backend/data/db.json` (gitignored; delete it to reseed), or, when `DATABASE_URL` is set, to Postgres (`lib/sql.ts`: Neon's HTTP driver, or a `useSql` test database), which every copy of the API shares. `ensureTables` makes the tables on first use and runs a `create table` once more when a copy starting at the same moment made it first (Postgres answers 23505 or 42P07 then). Each write carries the version it builds on (`StaleWrite` when another copy wrote first), and with shared storage each `/api` request first calls `refreshDatabase()`, which reads the data again when the stored version moved on (at most every `freshness.everyMs` for reads; always for writes, and for a Bearer token no session here matches, so a login on another copy isn't answered with a 401; each check waits at most `freshness.timeoutMs`). A save pushed back by another copy throws `SaveConflict` (503). The QR routes in `routes/checkin.ts` wrap their change and save in `retryConflicts`, which runs them again on the newer data up to `conflictRetry.attempts` times; so does the login that opens a session; other routes answer the 503 and the person tries again. Queries through Neon's driver are cut off after `sqlTimeoutMs` (`lib/sql.ts`). Everything still shares one document, so writes from different copies take turns; `store.postgres.test.ts` checks the agreed peak (200 scans at once from one address, for a 9,000-person event) against another writer in one process, not real traffic across Neon. Agreement photos go through `lib/photos.ts` (files under `uploads/`, or rows in Postgres).
- Vercel runs the built frontend as static files and the API as one function, `api/index.mjs` → `backend/src/vercel.ts` (it loads the data on each copy's first request through `createApp`'s `loaded`); `vercel.json` holds the build, the routes (the app's addresses, as in `appPaths.ts`, get `index.html`; anything else gets `404.html`, a copy of it the frontend build makes, with a 404 status; the rewrites match strictly, so `trailingSlash: false` first redirects an address ending in a slash to the one without it), the region (`sin1`, beside the Neon database) and the security headers, which must match `app.ts` (a test compares them). Background work after a response needs `waitUntil` from `@vercel/functions`, as `notify` does; nothing may rely on timers or files lasting there.

## Conventions

- The UI is in Korean or English (`frontend/src/i18n`): the choice made in 내 정보's 언어 row or with the footer's switch, else Korean when the browser's first language is Korean and English for any other (Korean in unit tests, which have no window). Copy is written in Korean and wrapped in `t("…", values)`; the Korean is the key and its English lives in `i18n/en/<area>.ts` (`{name}` parts filled from `values`). Never translate values used in logic (roles, NavLabels, statuses, sponsor kinds, tab values): show them with `t(value)`, and keep their English in `i18n/en/common.ts`. `i18n/coverage.test.ts` fails for a `t()` sentence without English, `i18n/lists.test.ts` for a listed value. Dates and money follow the language (`lib/date.ts`, `formatWon`, `fullWon`, `manWon`/`wonUnit`). The client sends the language as `Accept-Language`; the server still writes its messages in Korean and answers them in English through `backend/src/lib/i18n.ts` and `backend/src/i18n/en.ts` (`{name}` patterns for messages with a value). The legal pages show an English translation with a note that the Korean original prevails. Emails are in the account's `language` (set at sign-up from the page's language, and by the app whenever the one it shows differs, through `PUT /api/auth/preferences`): `notify` and the code emails put each Korean line through `translate`, so a new email line needs its English (a `{name}` pattern when it has a value) in `backend/src/i18n/en.ts`.

- `frontend/src/types.ts` mirrors the API shapes in `backend/src/types.ts`.
- Account types and sponsor types are listed in both `backend/src/lib/validation.ts` and the frontend (`data/roles.ts`, `data/sponsorTypes.ts`). Change them together. The frontend shows account types in groups (`accountTypeGroups`, flattening to the same order), and `catalog.ts` files each under one of the eight industries the match and the marks use; a renamed type goes in `renamedAccountTypes`, which the store applies on load. Sign-up asks for the person running the account (`contact`: name, position, a mobile number stored as 010-1234-5678 by `parseContact`), changed from 내 정보 (`PUT /api/auth/contact`, `modals/ContactModal.tsx`) and shown to no one but the two sides of an accepted proposal, on its agreement; the privacy policy says so. The position is picked from `positionHints` (`components/PositionField.tsx`, a select with 직접 입력 for any other), kept in Korean and shown through `t()`. A new password (sign-up, reset, change) is 8 to 64 characters with an English letter, a number and a symbol and no spaces: `checkPassword` in `validation.ts` and `lib/password.ts` with `components/PasswordRules.tsx` under the boxes (`lists.sync.test.ts` checks they agree). The same goes for profile fact labels and SNS platforms (`validation.ts` and `data/profile.ts`) and question kinds (`data/inquiries.ts`); `frontend/src/lib/lists.sync.test.ts` fails when they differ.
- 일괄 제안: a brand member picks up to 10 groups on 단체 찾기 (`여러 곳에 제안`, `maxBulk` in `pages/GroupsPage.tsx`) and sends one campaign and message to each through `POST /api/proposals` in turn (App's `sendMany`, `ProposeModal` with `targets`), each message's `{상대}` filled with that group's name; each still meets the usual checks, and those that failed are named.
- 제안 문구 템플릿: a member keeps up to 10 proposal messages on its account (`templates`, `PUT /api/auth/templates`, never the demo accounts), picked and saved in `ProposeModal`; the partner's and event's names are saved as `{상대}`/`{행사}` and filled in when used (`fillTemplate`). They come with `/me` and the export, go with the account, and the privacy policy lists them.
- Proposals go both ways through `POST /api/proposals`: a student group's reaches a brand with an account as a `SponsorRequest` (`/api/requests`, the brand's 받은 제안), a brand's reaches a group with an account as a `SponsorOffer` (`/api/offers`, the group's 받은 협찬, `pages/OffersPage.tsx`). Both inboxes share `components/RequestProgress.tsx` and the `request-*` classes, and `/api/proposals` answers each side's statuses and `sent`, the account's own requests or offers (partner, its event, what it offered, status), which both inboxes list under 검토 중 beside the received ones with 제안 취소 (`components/SentProposals.tsx`). A proposal to a partner with an account is about an event or campaign of the sender's that has not ended, picked in `modals/ProposeModal.tsx` (`eventId`, the next one when left out; another account's is 404, an ended one 409) with the sender's note (`message`, 300 characters at most, the usual greeting when empty, shown on both inboxes' cards and in the email), and needs one (409 otherwise), so an accepted one always becomes a dated sponsorship; one waiting for an answer is not sent twice, an accepted one can be sent again only about a later event, and withdrawing then takes back only the waiting one. One still waiting once its event has ended is closed (`마감`, `statusOf` in `lib/proposals.ts`, worked out wherever it is shown or answered and never stored): it can't be answered (409), both inboxes show it under its own 마감 tab, and it doesn't hold back a new proposal to the same partner.
- A listing's `logo` is a PNG, JPEG or WebP data URL of about 100KB at most, resized in the browser (`lib/image.ts`) and checked in `routes/profile.ts` (left out keeps it, null removes it); it lives in db.json for now.
- The brand and group catalogs are editable listings: each account's own listing is linked by `brandId`/`groupId` and edited from 내 정보. Recommended matches are the other catalog's top three, worked out in `backend/src/lib/catalog.ts`.
- Members (accounts that signed up) see only members' listings. The seed catalog and the demo accounts' listings are the examples, seen by visitors and by the shared demo accounts, which stay as trial logins; the login popup logs into either with one press (`data/demo.ts`, kept equal to the seed by `lib/lists.sync.test.ts`). The two never meet: `shownTo`/`shownCatalog` in `lib/catalog.ts` decide the catalogs and matches, proposals and conversations accept only a partner the account sees (404 otherwise), a member's proposal list and conversations leave out the examples, 가까운 순 shows a shop as its brand only to those who see that brand, and the demo group can't invite shops (403), as an invitation reaches a real owner. A member's empty catalog says so with what to do meanwhile (`components/CatalogEmpty.tsx`, once App's `catalogReady` says it has loaded), and 추천's heading stops claiming it found any. App empties every list in the same render the viewer changes (`listsFor`; an effect would draw the last viewer's data for a frame), so the examples never flash after logging in. The bell lists only what exists (no recommendation notice without matches). Each notice lists its `parts` (each offer, match or near day it counts) and is unread while one isn't in the account's `readNotices`; opening it or 모두 읽음 saves the parts on show through `PUT /api/auth/notices`, replacing the list, so every device shows the same dot and the list stays short. The dot shows only while a notice is unread. Each listing's `score` (55–98), `reasons` and `scoreParts` (each part as a share of its best, 0 to 1, with a short label the detail page shows as a bar; the labels' English is listed in `i18n/lists.test.ts`) are worked out for the account browsing, or the demo account of that side for visitors, in `backend/src/lib/matchScore.ts`: industry fit 35, shared tag words 15, track record 20 (a brand's sponsorships, a group's event size), sponsored together before 15, ready to answer 15. The `score` stored on a listing is not used.
- Distances on the catalogs (단체 찾기's 가까운 순 tab, the pin chip on `WorkCard`) are straight-line km between a group's campus and a brand's store, worked out in `browse()` with `lib/geo.ts`. A campus comes from the table in `backend/src/data/campuses.ts` (each university's own feature in OpenStreetMap, with its road address beside it; add schools the same way), found by the account's email domain, else the school name. A brand's store is `location` on its listing, written as `address` from 내 정보 and placed on the map through OpenStreetMap's Nominatim (`lib/geocode.ts`) only when `NOMINATIM_URL` is set (`backend/dev.env` sets the public server; it takes one request a second, so lookups are spaced 1.1s apart, and its ODbL data may be kept with the `Map data © OpenStreetMap contributors` credit in the footer). Never store coordinates from Kakao's or VWorld's geocoders: both allow live use only. Catalog version 4 dropped the Kakao coordinates saved before. Without coordinates there is no distance, and the save notice and the edit form say so. `browse()` also sends `mapOffset` (metres east and north of the viewer, to 10 m, `offsetMetres`), which draws the catalogs' 목록 · 지도 switch (`components/CatalogMap.tsx` with `LayoutSwitch`, on 추천 매칭 and 단체 찾기 beside the search and filters, which apply to it): the same sketch as 가까운 순 on kilometre scales (`catalogScale`), a dot per listing opening its card beside the map, and the listings without a place named under it. Tests and the e2e server run without a geocoder or a Kakao key. Distance never changes the match score. The privacy policy names the OpenStreetMap Foundation for this.
- The 가까운 순 tab on 추천 매칭 (`components/NearbyPlaces.tsx`) lists real shops around the student group's campus from Kakao Local's category search (visitors get made-up shops around the demo group's campus instead, `data/exampleShops.ts` through `exampleNearby`, marked `example`, with no map page or phone, and Kakao isn't asked), as the other tabs' cards (WorkCard's classes) with 협약 전 where a partner's card offers a proposal: every kind merged at first (`category=all`, the nearest 30), or one kind. Each card shows the shop's name's first letter, a joined brand its own logo; `GET /api/places` in `routes/places.ts` with `lib/places.ts`, the kinds listed in `validation.ts` and `data/places.ts`. Kakao allows Local API results only as live answers shown on screen: never store or cache them (only a place's ID and Kakao Map URL may be kept), so each look asks Kakao again and the route is rate-limited per address instead, counting each kind asked. Tests swap `placeSearch.search`. Each shop comes with its point, used only to draw `components/PlaceMap.tsx` (the 목록 · 지도 switch: a sketch around the campus, scaled to the farthest shop by `lib/placeMap.ts`, with stacked dots spread apart), never kept. With a Kakao JavaScript key (`KAKAO_JS_KEY`, limited to the site's domains in Kakao's console; `/api/site` hands it out as `maps.kakao`) the same dots and a campus pin are drawn as CustomOverlays on Kakao's map (`components/KakaoMap.tsx`, the SDK loaded from `dapi.kakao.com`, allowed in the Content-Security-Policy with `t1.daumcdn.net` and `t1.kakaocdn.net`, where it fetches the rest of itself; a load that never finishes falls back after 10 seconds), and the sketch stays for no key or a failed load. A 협약 전 shop can be invited (`routes/invites.ts`, `modals/InviteShopModal.tsx`): a `ShopInvite` in `Database.invites` keeps only the place's ID and Kakao Map URL, and its page `/invite/<code>` (`pages/InvitePage.tsx`, the brand side for visitors) lets the owner sign up as a brand and link the shop with one press, which lists the brand at once with `kakaoPlaceId` on its listing (one shop per brand, one brand per shop) and emails the groups that invited it; 가까운 순 then shows that shop as the brand, with a proposal.
- 친구 초대: a member's link (`/?ref=<code>`, `referralCode` made by `GET /api/auth/referral`, never for the demo accounts or co-admins) is kept for the tab by `keepReferral` and sent with sign-up (`referral`), which ties the new account (`referredBy`). Its first accepted sponsorship rewards the inviter once (`rewardReferrals` in `lib/referrals.ts`, from the request and offer accept routes, `referralRewardedAt`): a brand gets `referralRewardDays` (30) of Partners through `grantPartners`, a group is counted only, and the inviter is emailed. 내 정보's 친구 초대 card shows the link and the counts. Leaving clears `referredBy` pointing at the account; the privacy policy lists it.
- 비교: on 추천 매칭 and 단체 찾기 each card's 비교 button puts it in a tray at the bottom (`components/CompareTray.tsx`, `useCompare`, up to 3, not while picking groups for one offer), and 나란히 비교하기 opens a table of them: the match and each score part, distance, reviews, industry or field, school or store, a group's next event and audience, the offer, business check and tags, the best of each figure marked.
- An event's budget shows on its page only to the group and the brands it asked about that event (`seesBudget` in `routes/events.ts`).
- Icons are `components/Icon.tsx`: Lucide's from Iconify (ISC), won from Tabler (MIT), kept in the file so no page calls Iconify; a new one is copied in the same way.
- Search boxes end in `components/SearchClear.tsx`, an X shown while they hold words, in place of the browser's own.
- The catalogs can be searched (`components/CatalogSearch.tsx`, `matchesQuery` in `lib/search.ts`: every word typed, in name, kind, offer, tags, school or event), and 단체 찾기 also filters by the next event's size, month and kind, and by region and school (`matchesGroupFilters`): a region (`data/universities.ts`, the 17 provinces and cities with their universities) lists every university there in the school filter and keeps that region's groups.
- A brand writes its offers on 소개 편집 as rows like its SNS, each a kind from `brandOffers` (`validation.ts` and `data/profile.ts`, `lists.sync.test.ts` checks) and what of it ("150장"), saved as `offers` (`BrandOffer`) with the offer line made from them (`offerLine` in `routes/profile.ts`); what it can't edit sits apart in a locked card. Its portfolio's 불러오기 opens past sponsorships (a brand) or past events (a group) from `GET /api/profile/history` (`lib/portfolioHistory.ts`) to add as rows, and finds its store with Kakao's address search (`lib/postcode.ts`, allowed as `postcode.map.kakao.com` in the CSP's frame-src); it types no tags, 기본 정보 or follower counts. A member brand's 위치, 제공 서비스, 선호 행사, 평균 응답 and tags are worked out each time it is shown (`lib/brandProfile.ts`, from its address, offers, sponsored events' kinds and answer times); the examples keep their seeded ones, and no brand shows follower counts. Search and filters apply to whichever tab is open and stay when the tab changes.
- Student groups and brands have separate menus and pages (`data/navigation.ts`); `/event/<id>` is `pages/CampaignDetailPage.tsx` for a brand's own campaign (worked out from App's `events`) and `pages/EventDetailPage.tsx` for a group's event. A feature for one side gets its own page rather than a role branch inside the other side's page.
- Every screen is a `View` with its own address (`lib/route.ts`), title and description (`lib/pageMeta.ts`). `/` is the introduction for visitors (`home`, `pages/LandingPage.tsx`) and the dashboard lives at `/dashboard`; a member opening `/` goes on to the dashboard, and nothing shows there while a saved session is checked. History entries keep their view, and `entryView` drops one that no longer fits its address (kept from before the dashboard moved). An address no screen has becomes a `missing` view, the 404 page; `backend/src/lib/appPaths.ts` lists the same addresses so the server answers the rest with a real 404, and `vercel.json`'s rewrites list them again for Vercel, so change the three together (`appPaths.sync.test.ts` checks). Screens for one account or one link, and the dashboard, carry `noindex` in their meta (`keepOutOfSearch`, also called by the check-in pages); the rest are open to search engines (`robots.index` in `frontend/site.config.json`, `public/robots.txt`); `/sitemap.xml` is made at build from site.json's `url` and `sitemap` (`lib/sitemap.ts` through vite.config.ts; `lib/sitemap.test.ts` checks each page is a real, indexable screen and that robots.txt's `Sitemap:` matches), and site.json's `verification` codes (Google, Naver) become meta tags once set, and `public/llms.txt` describes the site for AI agents. Change screens through App's `go` and `goBack`, never by setting state directly, so the browser's back and forward buttons and swipe gestures keep working. `lib/swipe.ts` adds swiping anywhere on the page through those entries (one finger, or two on a trackpad: left to right goes back, right to left forward), leaving swipes from the screen edge to the browser; `go` tells it through `noteHistoryEnd` how far forward history reaches, and the screen a swipe brings slides in from that side (`data-swiped` in the "Motion" section).
- Popups go inside `<Presence>` (`components/Presence.tsx`) so they animate closed however they are closed.
- Password, PIN and token boxes are `components/PasswordField.tsx`: the label with its input and an eye button inside the box that shows what was typed (`aria-pressed`, one fixed name such as 비밀번호 보기, which must not contain the field's label, or `getByLabel` finds both). A new one uses it too.
- The scenes load three.js lazily (the chrome chain and rings download it once the page is idle after its first view, `whenIdle`, and start once they come near view, `whenNearView`, both in `lib/lite.ts`; fetched only near view it arrived after people had scrolled past), are left out for visitors who save data or are on a slow connection, and where WebGL would be drawn on the CPU (`liteScenes`; `hardwareWebGL` asks once for a context with `failIfMajorPerformanceCaveat`, which software rendering refuses, so PageSpeed's GPU-less test machines see the CSS backgrounds), pause off screen, hold still with reduced motion and leave a CSS background when WebGL is missing. Each live scene is its own WebGL context, so keep them few: a dashboard has three (hero, chain, footer rings), the introduction two (hero, footer rings), and other pages at most one besides the footer; the mesh draws through one shared context into images. A canvas keeps one context for life and React mounts effects twice in development, so a scene that loses its context on cleanup creates its canvas inside the effect (as `LayersGradient.tsx` does) or creates the context only after an async import. The getlayers.ai shaders are verbatim; retint them through their `config` only. The ShaderGradient (`components/GradientBackdrop.tsx`, lazily loaded `GradientScene.tsx`) heads only the login and sign-up popups (`<Modal banner>`). `three` is pinned to 0.182.0 because from r183 three warns that `THREE.Clock` is deprecated, and @react-three/fiber 9.8.1 still creates one for every canvas.
- The backend is ESM with NodeNext resolution, so relative imports end in `.js`.
- Express 5 forwards thrown and rejected errors to the error handler. Throw `HttpError(status, message)` with a Korean message the user can read.
- The UI is a light theme after getlayers.ai's Stride in deep blue and silver, with slate grays instead of black. Design tokens are CSS variables on `:root` in `index.css`: `--point` is the deep blue point color and text on it uses `--on-point` (`--point-strong` for blue text on white); `--point-bright` (on white) and `--point-glow` (on deep blue) are the accent blues for the words a block turns on, such as a heading's accent line; copy uses `--ink`, `--ink-soft` and `--muted`; silver fills use `--fill`/`--fill-strong` or `--silver-gradient` with `--silver-ring`; hairlines are `--line` or the inset `--ring`; dark tiles use `--slate`; goals met and not yet met use `--goal-met` (deep blue) and `--goal-short` (silver), and the goal line over them `--goal-mark` (amber). Use the tokens rather than new hex values. A deep blue surface also sets `--surface-tone: dark`, which tells the header to show the light logo over it. Copy over a moving gradient sits on a navy shade or frosted navy glass; check its contrast against the live canvas when moving it. The PDF report pages keep their own print colors on `.pdf-export`.
- Copy is short and says what the reader gets: at most two or three lines, a comma or full stop where a line should end, lists joined with ` · ` rather than commas. `components/Lines.tsx` breaks copy into lines after a comma (dropped) or a full stop, question or exclamation mark (kept); PageIntro descriptions, MeetingHero, ValuePoints, WhyUniconnect, JourneyChain, CatalogEmpty, DemoPreview and the introduction's rows use it. The header's logo is 38px tall (30px on phones).

The event's first sponsor, when it is the only one, takes over the event's coupon, PIN, counts and coupon numbers. `metrics` stays the whole event's for the group's report, which lists the shares as `report.sponsors`.
- When a write fails, `saveDatabase()` puts the data in memory back to what was last written and rejects with a 503 ("되돌렸어요") for that caller and for writes queued behind it, so a failed request leaves nothing behind and can be retried; later saves still run. When another copy of the API wrote first, the newer data comes in as well, and reading the data anew also turns away writes queued before it. Every write route mutates memory and then awaits `saveDatabase()`, and nothing else should change the data without saving. Look up request input in plain lookup objects with `Object.hasOwn`, so names like `constructor` are not found.
